# Key Principles

* **Focus on problems, not solutions.** Engineering is extremely sensitive to over-solutioning. PRDs must focus exclusively on business problems, business outcomes, and customer evidence — never prescribe implementation details. If you're describing system internals, APIs, database schemas, or technical architecture, you've gone too far. Stop and reframe as a user-facing capability or business outcome.
* **Evidence-first Business Case.** Always search Slack before writing the Business Case. Direct quotes from engineers and customers are more persuasive than generic problem descriptions.
* **Customer outcomes over features.** Emphasize what the customer needs to accomplish and why, not how to build it technically.
* **Part 1 / Part 2 split is mandatory.** Part 1 is for UX and Architects. Part 2 is for scrum teams. Never flatten them into one section.
* **One-pager is a first-class mode, not a fallback.** Writing a one-pager is the right move when the audience is engineering or UX/Architect and the goal is *less context, faster alignment*. Always ask which mode when the request is ambiguous. One-pagers are condensed, not under-researched — Slack research and portfolio cross-reference still run in full. They can be expanded to full PRDs incrementally via [expansion](../collaboration/expansion.md) without losing comments or decisions.
* **Graceful scope.** When the feature input is thin, make reasonable inferences and flag them as assumptions. Never block on missing information.
* **Acceptance Criteria must be testable outcomes.** Every AC must describe a specific, verifiable business outcome — not implementation steps.
* **Risks table must include mitigations.** Never leave the Mitigation column blank.
* **Post GA Ideas belong in the Appendix, not in scope.** If something is a future idea, put it there — not in Out of Scope.
* **Inline citations in Business Case.** When quoting Slack messages, include the message link as a citation next to the quote.
* **Always prompt for release.** Ask "What release is this PRD for?" before starting every PRD. Default to 262 only if the user explicitly says so — never assume silently.
* **Canvas creation is user-initiated, never automatic.** The skill never calls `slack_create_canvas` on its own — not during initial save, not after edits, not after comment review. Wait for the user to explicitly ask (e.g., "create the canvas", "publish to Slack") before invoking [canvas creation](../lifecycle/saving-and-delivery.md#canvas-creation-on-request-only).
* **PRD canvases are always created as personal canvases.** Never pass a `channel_id` to `slack_create_canvas` when creating a PRD canvas (one-pager or full). The user owns the canvas in their personal space and shares it with the right audience themselves. Auto-posting a PRD to a channel is out of scope.
* **Two-stage lifecycle — markdown-only vs. post-canvas.** While a PRD is still just a markdown file and no Slack canvas has been created, all changes are **clean rewrites** (see [pre-canvas rules](../lifecycle/updating-prds.md#markdown-only-pre-canvas--clean-rewrites)): use the Write tool, no strikethroughs, no change markers, consolidate everything. The rationale: no one else is commenting yet, so there's no edit history to preserve and change markers create noise during early drafting. Once the canvas is created, the skill switches to **incremental updates** (see [post-canvas rules](../lifecycle/updating-prds.md#post-canvas--incremental-updates)): additive content gets appended with `*Added:*`, conflicting content gets struck through with a blockquote replacement, and nothing is ever deleted. This two-stage model keeps early drafts readable and starts preserving audit trails the moment collaboration begins.
* **Comments drive iteration.** Canvas comments from collaborators (UX, Eng, QE, CX) are first-class input. Present them with attribution, suggest an action for each, and always wait for the user to decide before changing the PRD. Every accepted comment becomes a tracked incremental update with a reply confirming the change.
* **Version control friendly.** Save PRDs as markdown files so they can be tracked in git, reviewed in PRs, and collaborated on locally.
* **Portfolio-aware.** Every new PRD must be cross-referenced against existing PRDs in the portfolio. Check for dependency overlap, token budget conflicts, rollout sequencing issues, and synergy opportunities. Two PRDs that both add grounding data to the prompt but don't acknowledge each other's token budget impact is a planning failure. Surface these in the Appendix.
* **Collaborate, don't dictate.** Technical sections should describe "what needs to happen" not "how to implement it." Leave implementation decisions to engineering.
